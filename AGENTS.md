
# Project Instructions

## Project
Build Marc Arias Ortiz's personal homepage as a Linux-inspired,
terminal-first portfolio.

The website represents a real person and a professional portfolio.
It must balance technical personality, usability and professional credibility.

## Product principles
- Terminal-inspired, not a fake screenshot of a terminal.
- Personal, playful and technically credible.
- Easy to explore for both technical and non-technical visitors.
- Professional information must remain easy to find.
- Prefer working features over decorative complexity.
- Mobile support is a first-class requirement.

## Working agreement
- Read the relevant files in docs/ before starting a task.
- Work in small, explicit, reviewable increments.
- Do not implement the entire roadmap in one task.
- Inspect the existing project before choosing or changing its stack.
- Explain the plan before making substantial changes.
- Ask before introducing major dependencies or changing architecture.
- Do not overwrite existing work without understanding it.
- Keep documentation aligned with the implementation.

## Technical quality
- Use semantic, accessible HTML.
- Support keyboard navigation and visible focus states.
- Handle terminal input safely; never execute user input as a shell command.
- Do not expose secrets, credentials or private infrastructure details.
- Do not invent professional experience, achievements or project results.
- Avoid unnecessary dependencies and premature abstractions.
- Respect reduced-motion preferences.
- Validate changes using the project's available checks.

## Design direction
- Linux shell / personal home directory metaphor.
- Restrained cyberpunk: a functional terminal first, playful details last.
- Strong typography, subtle terminal details and purposeful interactions.
- Avoid generic SaaS landing page layouts, excessive glow and neon text.
- Humor should feel natural, not forced.
- Keep the interface usable on small screens.
- See docs/DESIGN.md for the palette, proportions and terminal behavior.

## Implementation workflow
For each task:
1. Inspect relevant files and current project state.
2. State the intended changes and acceptance criteria.
3. Implement only the requested scope.
4. Run relevant checks where available.
5. Summarize changes, checks and known limitations.
6. Identify the next smallest useful step.

Do not claim a check passed unless it was actually run.
